# Flex Bar API

Node.js, Express, and TypeScript API, designed for an independent Vercel deployment.

## Local setup

1. Copy `.env.example` to `.env` once. The example file is only a template: replace `SUPABASE_PUBLISHABLE_KEY` with the real publishable/anon key and `SUPABASE_SERVICE_ROLE_KEY` with the real service-role secret from Supabase Project Settings → API Keys. The project URL is prefilled. Placeholder values beginning with `your-` will not work. `.env` is gitignored; never put the service-role key in the frontend or share it in chat.
2. For a new Supabase database, open `supabase/schema.sql` in the SQL Editor and run it once. It sets up the complete schema, starter departments, a curated Nigerian beverage starter catalog, sales notifications, department sales defaults, and authenticated staff chat. Catalog entries start with zero stock, zero price, and no department assignment; an administrator must configure each item before it is available to sell. The catalog is not exhaustive and does not include product photos or brand logos. Upload product images that your business owns or is licensed to use from Inventory. Do not run this consolidated setup on a database that already has the old migrations applied; it is a fresh-database schema, not a migration for an existing database.
3. Run `npm run dev` from this folder. The dev/start scripts load `.env`. R2 credentials are only needed when enabling features that use file storage; they are not required to run attendance or geofence settings.
4. Check `http://localhost:3000/api/v1/health`.

`GET /api/v1/me` requires a valid email/password sign-in session and reads the signed-in user's profile under row-level security. The API returns the role stored in the database; a role is never accepted from the browser. The super-admin-only `/api/v1/admin` routes list staff accounts only (administrator accounts are excluded), create staff accounts with an admin-assigned initial password, assign app roles and departments, enable/lock staff access, send password-reset emails, reset staff lock PINs, archive/restore accounts, and permanently delete archived staff while retaining attendance history. Passwords are never returned to administrators or written to the activity log. The registration form includes seven bar/restaurant starter role-and-department assignments; enter each real staff member's name, email, and initial password. No fake staff accounts are created. Staff should receive their initial password through a secure channel and create a four-digit lock PIN at first sign-in. The workspace locks after 20 minutes idle, and five incorrect PIN attempts cause a 15-minute lockout. PINs are stored as salted hashes and never returned by the API. The protected primary admin cannot be disabled or demoted through staff-management routes. The `/api/v1/attendance` routes save the business geofence, let staff and management roles clock in/out from inside it, and show the admin attendance history; the super-admin is explicitly blocked from clocking in. Department changes, user creation/assignments, password resets, PIN resets, account archival/deletion, settings changes and geofence changes are recorded in the admin activity log. Configure `FRONTEND_URL` to the deployed frontend URL. Disable public sign-ups in Supabase Auth settings; the app itself has no public sign-up flow. The admin UID is an identifier, not a password—keep the admin account protected with a strong, unique password and never share it.

Cloudflare R2 is configured through server-only environment variables. The R2 client helper is ready for later file features; credentials are never sent to the frontend.

## Vercel

Create a Vercel project connected to the backend Git repository and leave its Root Directory at the repository root (`./`). This is a separate repository, so there is no nested `backend` directory in the deployment. `vercel.json` builds the Express app as a Node function and routes requests to it. Verify `https://<your-api-domain>/api/v1/health` returns `200` after deployment. Configure `SUPABASE_URL`, either `SUPABASE_PUBLISHABLE_KEY` or `SUPABASE_ANON_KEY`, the server-only `SUPABASE_SERVICE_ROLE_KEY`, `FRONTEND_URL`, `FRONTEND_ORIGINS`, and the R2 variables in Vercel project settings. Set `FRONTEND_URL` to the deployed frontend origin and include that exact origin in `FRONTEND_ORIGINS`; add any production custom domain origins as well, comma-separated. Set the frontend project's `VITE_API_BASE_URL` to `https://<your-api-domain>` with no port or `/api/v1` suffix. Redeploy both projects after changing environment variables. The service-role secret must only be added to the backend deployment, never to frontend `VITE_*` variables. Do not add secret values to `.env.example`.

Apply any unapplied SQL migrations to the intended Supabase environment before enabling their features. Staff accounts are created through the super-admin interface and Supabase Auth; new profiles default to the least-privileged `staff` role and inactive access until the route assigns their role and activates them. Disable public sign-ups in Supabase Auth settings.

For stock control, assign an active department head before dispatching inventory. Dispatch quantities and their sender/timestamp are recorded as pending deliveries; only that department's active head can confirm receipt, which then adds the quantity to available stock. Set a product's department and sale price in Inventory before selling it.

Department heads receive a Department Hub with their assigned team's active staff, clock-in state, completed sales, and submitted cash closes. Staff submit a daily cash reconciliation while clocked in; recorded cash sales are calculated from completed cash transactions, and the handover is assigned to the active department head. Once a staff member closes the shift, additional sales are blocked for that business day. Department heads can schedule meetings for their department. Administrators can schedule a meeting for any department and access every department meeting.

Meeting Room uses a single live-call flow with browser WebRTC media and private Supabase Realtime signaling. Participants join with their microphone; camera access is requested only when they choose Start camera. Anyone can stop their camera or share/stop sharing their screen while in the call. Animated sound-wave badges show detected voice activity on participant tiles. Calls are not recorded by this feature. Administrators can join any department call, are identified to participants, and start muted. Hidden administrator participation is not supported. Calls can connect peer-to-peer with the included STUN configuration; some corporate/mobile networks require a TURN relay. For reliable calls across restricted networks, configure backend-only TURN_URLS (comma-separated), TURN_USERNAME, and TURN_CREDENTIAL. Serve the frontend over HTTPS outside localhost so browsers permit microphone/camera/screen-sharing access.

Chat uses the existing authenticated staff accounts: any active staff member or administrator can start a private conversation with any other active colleague. Messages are stored in Supabase, protected by participant checks in the API and row-level security for real-time reads.

For an existing database, do not run the whole fresh-database supabase/schema.sql again. In Supabase SQL Editor, copy and run only the additive section at the end of that file, beginning at the comment 'Authenticated one-to-one staff messaging' and continuing to the end. It creates the chat tables with RLS enabled, adds the meeting voice/video mode column, and installs restricted Realtime signaling policies. Do not choose an option that runs the query without RLS. The old security prompt is expected if you ran the earlier schema version; the updated additive section enables RLS on chat_conversations, which is intentionally not directly readable by browser clients. No separate messaging login or third-party account is required.
