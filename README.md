# Flex Bar API

Node.js, Express, and TypeScript API, designed for an independent Vercel deployment.

## Local setup

1. Copy `.env.example` to `.env` once. The example file is only a template: replace `SUPABASE_PUBLISHABLE_KEY` with the real publishable/anon key and `SUPABASE_SERVICE_ROLE_KEY` with the real service-role secret from Supabase Project Settings → API Keys. The project URL is prefilled. Placeholder values beginning with `your-` will not work. `.env` is gitignored; never put the service-role key in the frontend or share it in chat.
2. For a new Supabase database, run `supabase/schema.sql` once, then run `supabase/migrations/20261017_company_workspaces.sql`, `supabase/migrations/20261017_instant_department_meetings.sql`, `supabase/migrations/20261018_in_app_calls.sql`, `supabase/migrations/20261019_repair_in_app_call_policies.sql`, `supabase/migrations/20261018_chat_receipts_typing.sql`, and `supabase/migrations/20261020_single_device_sessions.sql` in order. The company migration creates the Flex Bar company and assigns existing records to it; subsequent company registrations get isolated workspaces. Do not rerun the consolidated schema on an existing database.
3. Run `npm run dev` from this folder. The dev/start scripts load `.env`. R2 credentials are only needed when enabling features that use file storage; they are not required to run attendance or geofence settings.
4. Check `http://localhost:3000/api/v1/health`.

`GET /api/v1/me` requires a valid email/password sign-in session and reads the signed-in user's profile under row-level security. The API returns the role stored in the database; a role is never accepted from the browser. The `/api/v1/admin` routes manage staff, departments, and settings within the signed-in administrator's company. Passwords are never returned to administrators or written to the activity log. Staff should receive initial passwords through a secure channel and create a four-digit lock PIN at first sign-in. The workspace locks after 20 minutes idle, and five incorrect PIN attempts cause a 15-minute lockout. PINs are stored as salted hashes and never returned by the API. The primary administrator cannot be disabled or demoted through staff-management routes. Attendance settings and activity history are company-specific; super-admin accounts are explicitly blocked from clocking in. Configure `FRONTEND_URL` to the deployed frontend URL. For company registration, enable Supabase Auth public sign-ups with email confirmation; the standalone page is available at `/signup` and is not linked from the existing sign-in screen. The auth trigger provisions the selected company workspace and grants its creator company-admin access.

Cloudflare R2 is configured through server-only environment variables. The R2 client helper is ready for later file features; credentials are never sent to the frontend.

## Vercel

Create a Vercel project connected to the backend Git repository and leave its Root Directory at the repository root (`./`). This is a separate repository, so there is no nested `backend` directory in the deployment. `vercel.json` builds the Express app as a Node function and routes requests to it. Verify `https://<your-api-domain>/api/v1/health` returns `200` after deployment. Configure `SUPABASE_URL`, either `SUPABASE_PUBLISHABLE_KEY` or `SUPABASE_ANON_KEY`, the server-only `SUPABASE_SERVICE_ROLE_KEY`, `FRONTEND_URL`, `FRONTEND_ORIGINS`, and the R2 variables in Vercel project settings. Set `FRONTEND_URL` to the deployed frontend origin and include that exact origin in `FRONTEND_ORIGINS`; add any production custom domain origins as well, comma-separated. Set the frontend project's `VITE_API_BASE_URL` to `https://<your-api-domain>` with no port or `/api/v1` suffix. Redeploy both projects after changing environment variables. The service-role secret must only be added to the backend deployment, never to frontend `VITE_*` variables. Do not add secret values to `.env.example`.

Apply any unapplied SQL migrations to the intended Supabase environment before enabling their features. For an existing database, do not rerun the consolidated `schema.sql`; apply the company-workspace, instant-meeting, in-app-call, chat receipt/typing, and single-device-session migrations in order in Supabase SQL Editor. The company migration is safe to rerun if a prior attempt stopped on an already-existing constraint or index. The single-device-session migration is required before deploying the matching API/frontend: explicitly signing in on a new device replaces the previous device session, and the old device is signed out on its next API request or heartbeat. Restoring an existing session does not take over an active session on another device. Enable Auth public sign-ups with email confirmation only when ready to accept company registrations.

For stock control, assign an active department head before dispatching inventory. Dispatch quantities and their sender/timestamp are recorded as pending deliveries; only that department's active head can confirm receipt, which then adds the quantity to available stock. Set a product's department and sale price in Inventory before selling it.

Department heads receive a Department Hub with their assigned team's active staff, clock-in state, completed sales, and submitted cash closes. Staff submit a daily cash reconciliation while clocked in; recorded cash sales are calculated from completed cash transactions, and the handover is assigned to the active department head. Once a staff member closes the shift, additional sales are blocked for that business day. Department heads can start an instant meeting or schedule one for their department. Administrators can start or schedule a meeting for any department and access every department meeting. Instant meetings are available to join immediately and remain accessible for up to eight hours; scheduled rooms open 15 minutes before their start time.

Meeting Room uses a single live-call flow with browser WebRTC media and private Supabase Realtime signaling. Participants join with their microphone; camera access is requested only when they choose Start camera. Anyone can stop their camera or share/stop sharing their screen while in the call. Animated sound-wave badges show detected voice activity on participant tiles. Calls are not recorded by this feature. Administrators can join any department call, are identified to participants, and start muted. Hidden administrator participation is not supported. Calls can connect peer-to-peer with the included STUN configuration; some corporate/mobile networks require a TURN relay. For reliable calls across restricted networks, configure backend-only TURN_URLS (comma-separated), TURN_USERNAME, and TURN_CREDENTIAL. Serve the frontend over HTTPS outside localhost so browsers permit microphone/camera/screen-sharing access.

Chat uses the existing authenticated staff accounts: any active staff member or administrator can start a private conversation with any other active colleague. Messages are stored in Supabase, protected by participant checks in the API and row-level security for real-time reads.

Chat supports one-to-one voice/video calls and private group calls with up to seven invited colleagues. A joined participant can invite active colleagues from the same company to an existing call, up to eight participants total. Hanging up in a two-person call ends it for both people; in a group call, only the person hanging up leaves. Incoming calls are shown inside the signed-in app. Signing out closes the user's call sessions; starting a new call also clears any stale call left by an earlier session. The in-app calling migration must be applied before calls are available; browser microphone/camera permission and HTTPS are required. Video starts with the camera when selected, and participants can turn on video during a voice call or switch their camera off.

For an existing database, do not run the whole fresh-database `supabase/schema.sql` again. Apply any unapplied company-workspace, instant-meeting, in-app-calls, chat receipts/typing, and single-device-session migrations in order. If calls fail to join their private Realtime room, run the latest idempotent `20261019_repair_in_app_call_policies.sql` in Supabase SQL Editor to recreate the participant-authorized room function and Realtime policies and grant the authenticated role the required `realtime` schema/table privileges; RLS remains enabled and restricts access to call participants. Always use the workspace copy of this repair migration, not an older saved copy. Then reload the frontend so it refreshes the Realtime JWT before joining. Apply `20261018_chat_receipts_typing.sql` if chat receipts and typing are needed. The chat migration adds message delivery receipts, participant-authorized private typing presence, and notification support for chat messages. Explicitly signing in on a new device replaces the account's active device session; the previous device is denied API access and signs out on its next request or heartbeat. Restoring a session does not take over another active device. Do not choose an option that runs queries without RLS. Calls require the active participant's authenticated account; configuring TURN_URLS, TURN_USERNAME and TURN_CREDENTIAL on the backend improves connectivity on restricted networks.
