# Flex Bar API

Node.js, Express, and TypeScript API, designed for an independent Vercel deployment.

## Local setup

1. Copy `.env.example` to `.env` once. The example file is only a template: replace `SUPABASE_PUBLISHABLE_KEY` with the real publishable/anon key and `SUPABASE_SERVICE_ROLE_KEY` with the real service-role secret from Supabase Project Settings → API Keys. The project URL is prefilled. Placeholder values beginning with `your-` will not work. `.env` is gitignored; never put the service-role key in the frontend or share it in chat.
2. For a new Supabase database, run `supabase/schema.sql` once, then run the migrations in chronological order: `20261017_company_workspaces.sql`, `20261017_instant_department_meetings.sql`, `20261018_in_app_calls.sql`, `20261018_chat_receipts_typing.sql`, `20261019_repair_in_app_call_policies.sql`, `20261019_chat_voice_messages.sql`, `20261020_single_device_sessions.sql`, `20261021_call_push_subscriptions.sql`, `20261022_multiple_device_push_sessions.sql`, and `20261023_attendance_geofence_qr.sql`. The company migration creates the Flex Bar company and assigns existing records to it; subsequent company registrations get isolated workspaces. Do not rerun the consolidated schema on an existing database.
3. Run `npm run dev` from this folder. The dev/start scripts load `.env`. R2 credentials are only needed when enabling features that use file storage; they are not required to run attendance or geofence settings.
4. Check `http://localhost:3000/api/v1/health`.

`GET /api/v1/me` requires a valid email/password sign-in session and reads the signed-in user's profile under row-level security. The API returns the role stored in the database; a role is never accepted from the browser. The `/api/v1/admin` routes manage staff, departments, and settings within the signed-in administrator's company. Passwords are never returned to administrators or written to the activity log. Staff should receive initial passwords through a secure channel and create a four-digit lock PIN at first sign-in. The workspace locks after 20 minutes idle, and five incorrect PIN attempts cause a 15-minute lockout. PINs are stored as salted hashes and never returned by the API. The primary administrator cannot be disabled or demoted through staff-management routes. Attendance settings and activity history are company-specific; super-admin accounts are explicitly blocked from clocking in. Configure `FRONTEND_URL` to the deployed frontend URL. For company registration, enable Supabase Auth public sign-ups with email confirmation; the standalone page is available at `/signup` and is not linked from the existing sign-in screen. The auth trigger provisions the selected company workspace and grants its creator company-admin access.

Attendance check-in/out requires a precise reported location that, including its reported accuracy, falls within 10 metres of the company's saved location, plus a valid rotating on-site QR code. Administrators display the QR from Settings → Business Location / Geofence; staff scan it from Attendance. The QR changes every 30 seconds; the current and immediately previous code are accepted to tolerate scanning at a rotation boundary. Codes are signed using the backend-only Supabase service-role key, so no extra environment variable is needed. An attempted clock-in that cannot be confirmed within the geofence is recorded without storing precise coordinates and creates workspace notifications for active company administrators and the staff member's active department head (notification delivery is limited to once per staff member per five minutes). These inserts also use the configured notifications webhook for push delivery. Apply `20261023_attendance_geofence_qr.sql` before deploying this enforcement; it sets existing geofence radii to 10 metres, fixes the database constraint, and creates the private geofence-attempt audit table. Browser GPS and QR codes are not hardware attestation: a QR can be photographed or relayed before it expires, so this raises the bar for off-site check-ins but cannot prove physical presence against a deliberate relay.

Cloudflare R2 is configured through server-only environment variables. The R2 client helper is ready for later file features; credentials are never sent to the frontend.

## Incoming call push

For an existing database, apply `supabase/migrations/20261021_call_push_subscriptions.sql` after `20261020_single_device_sessions.sql`, then apply `20261022_multiple_device_push_sessions.sql`. The latter permits multiple signed-in devices per account, while each device keeps its own push subscription. Generate a VAPID key pair from this folder with `npx web-push generate-vapid-keys`, then set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` in the backend environment. Keep the private key backend-only. Add the same keys to local `.env` for local testing and to the backend Vercel project's environment before redeploying.

Keep the generated public and private keys together: the public key must be a valid 65-byte P-256 key (87 unpadded base64url characters), and the private key must be its matching 32-byte value. If the browser reports an `atob` decoding error or call alerts cannot be enabled, generate a fresh pair, replace both backend environment values, and redeploy the backend. Never put the private key in frontend environment variables.

To deliver every workspace notification while the app is closed, also set a random `PUSH_WEBHOOK_SECRET` in the backend environment, then create a Supabase Database Webhook for `public.notifications` on `INSERT`. Use `POST https://<backend-domain>/api/v1/push-notifications/webhook` and add `Authorization: Bearer <PUSH_WEBHOOK_SECRET>` as a request header. Keep that secret identical in Supabase and the backend deployment. The webhook handles all notification rows; users still need to enable browser notifications from Notifications on each device, and the PWA must have been installed/opened at least once there.how do i create all this in my supabase

For the message webhook, create a random secret (for example, `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`). Add it as `PUSH_WEBHOOK_SECRET` in the backend deployment. In Supabase Dashboard, open **Database → Webhooks**, create an HTTP webhook for schema `public`, table `notifications`, event `INSERT`, and point it to `https://<backend-domain>/api/v1/push-notifications/webhook`. Add the header `Authorization` with value `Bearer <same-secret>`. Save the webhook and keep the secret backend-only.

## Vercel

Create a Vercel project connected to the backend Git repository and leave its Root Directory at the repository root (`./`). This is a separate repository, so there is no nested `backend` directory in the deployment. `vercel.json` builds the Express app as a Node function and routes requests to it. Verify `https://<your-api-domain>/api/v1/health` returns `200` after deployment. Configure `SUPABASE_URL`, either `SUPABASE_PUBLISHABLE_KEY` or `SUPABASE_ANON_KEY`, the server-only `SUPABASE_SERVICE_ROLE_KEY`, `FRONTEND_URL`, `FRONTEND_ORIGINS`, and the R2 variables in Vercel project settings. Set `FRONTEND_URL` to the deployed frontend origin and include that exact origin in `FRONTEND_ORIGINS`; add any production custom domain origins as well, comma-separated. Set the frontend project's `VITE_API_BASE_URL` to `https://<your-api-domain>` with no port or `/api/v1` suffix. Redeploy both projects after changing environment variables. The service-role secret must only be added to the backend deployment, never to frontend `VITE_*` variables. Do not add secret values to `.env.example`.

Apply any unapplied SQL migrations to the intended Supabase environment before enabling their features. For an existing database, do not rerun the consolidated `schema.sql`; apply the company-workspace, instant-meeting, in-app-call, chat receipt/typing, chat voice-message, single-device-session, call-push, multiple-device-push-session, and `20261023_attendance_geofence_qr.sql` migrations in chronological order in Supabase SQL Editor. The company migration is safe to rerun if a prior attempt stopped on an already-existing constraint or index. Apply `20261022_multiple_device_push_sessions.sql` before deploying the matching backend/frontend so the same account can remain signed in on phone and desktop. Enable Auth public sign-ups with email confirmation only when ready to accept company registrations.

For stock control, assign an active department head before dispatching inventory. Dispatch quantities and their sender/timestamp are recorded as pending deliveries; only that department's active head can confirm receipt, which then adds the quantity to available stock. Set a product's department and sale price in Inventory before selling it.

Department heads receive a Department Hub with their assigned team's active staff, clock-in state, completed sales, and submitted cash closes. Staff submit a daily cash reconciliation while clocked in; recorded cash sales are calculated from completed cash transactions, and the handover is assigned to the active department head. Once a staff member closes the shift, additional sales are blocked for that business day. Department heads can start an instant meeting or schedule one for their department. Administrators can start or schedule a meeting for any department and access every department meeting. Instant meetings are available to join immediately and remain accessible for up to eight hours; scheduled rooms open 15 minutes before their start time.

Meeting Room and Chat calls use browser WebRTC media and private Supabase Realtime signaling. Participants join with their microphone; camera access is requested only when they choose Start camera. Anyone can stop their camera or share/stop sharing their screen while in the call. Animated sound-wave badges show detected voice activity on participant tiles. Calls are not recorded by this feature. Administrators can join any department call, are identified to participants, and start muted. Hidden administrator participation is not supported. Calls can connect peer-to-peer with the included STUN configuration; some corporate/mobile networks require a TURN relay. For Metered Open Relay, configure `METERED_APP_NAME` (the subdomain shown in the Metered dashboard) and the private TURN REST `METERED_API_KEY` in the backend's Vercel Production environment. The backend requests Metered's ICE server list server-side when a call room is opened, so the API key is never sent to browsers. Alternatively, configure a TURN provider's `turn:` or `turns:` URLs (comma-separated), username, and credential as backend-only `TURN_URLS`, `TURN_USERNAME`, and `TURN_CREDENTIAL`. A `stun:` URL alone cannot relay media. Redeploy the backend after configuring these variables. Serve the frontend over HTTPS outside localhost so browsers permit microphone/camera/screen-sharing access.

Chat uses the existing authenticated staff accounts: any active staff member or administrator can start a private conversation with any other active colleague. Messages are stored in Supabase, protected by participant checks in the API and row-level security for real-time reads.

Chat supports one-to-one voice/video calls and private group calls with up to seven invited colleagues. A joined participant can invite active colleagues from the same company to an existing call, up to eight participants total. Hanging up in a two-person call ends it for both people; in a group call, only the person hanging up leaves. Incoming calls show the caller's name, position, and profile photo when available. Each unanswered invitation expires after one minute; unanswered calls appear in the direct chat with a call-back action. Signing out closes the user's call sessions; starting a new call also clears any stale call left by an earlier session. The in-app calling migration must be applied before calls are available; browser microphone/camera permission and HTTPS are required. Video starts with the camera when selected, and participants can turn on video during a voice call or switch their camera off.

Chat voice messages require the `20261019_chat_voice_messages.sql` migration. It creates a private Supabase Storage bucket limited to audio recordings and policies that let only active participants of a conversation upload/read its recordings. Voice messages are recorded in the browser (up to two minutes) and require microphone permission and HTTPS outside localhost.

For an existing database, do not run the whole fresh-database `supabase/schema.sql` again. Apply any unapplied company-workspace, instant-meeting, in-app-calls, chat receipts/typing, single-device-session, and call-push migrations in order. The call-push migration also allows multiple signed-in devices per account so each device can maintain its own push subscription. If calls fail to join their private Realtime room, run the latest idempotent `20261019_repair_in_app_call_policies.sql` in Supabase SQL Editor to recreate the participant-authorized room function and Realtime policies and grant the authenticated role the required `realtime` schema/table privileges; RLS remains enabled and restricts access to call participants. Always use the workspace copy of this repair migration, not an older saved copy. Then reload the frontend so it refreshes the Realtime JWT before joining. Apply `20261018_chat_receipts_typing.sql` if chat receipts and typing are needed. The chat migration adds message delivery receipts, participant-authorized private typing presence, and notification support for chat messages. Do not choose an option that runs queries without RLS. Calls require the active participant's authenticated account; configuring TURN_URLS, TURN_USERNAME and TURN_CREDENTIAL on the backend improves connectivity on restricted networks.
